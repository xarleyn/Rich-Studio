# 0023. Вход владельца через Telegram

Дата: 2026-10-31. Продолжение [0014](0014-public-telegram-accounts.md) и [0019](0019-account-tokens.md).

**Решение.** Владелец сервиса определяется подписанным Telegram-входом: если Telegram ID вошедшего равен `TG_OWNER_ID`, открывается сессия в корневой таблице `sessions` с заполненным `telegram_id` и правами admin в корневом рабочем пространстве. Для владельца не вызываются создание учётки (`accounts.initialize`), запись в реестре аккаунтов и `account_sessions`: ни папки `accounts/<id>`, ни строки в реестре, фоновые циклы учётку владельца не итерируют. Публичные пользователи и обычный путь входа не меняются.

Сессия владельца сверяется с текущим значением `TG_OWNER_ID` на каждый запрос: снятие или смена переменной перестаёт принимать прежние сессии — тот же принцип, что у сессии `STUDIO_API_KEY`, умирающей при смене ключа. Уровень у сессии не хранится: она либо совпадает с настроенным владельцем (admin), либо недействительна.

Кнопка «Вход владельца сервиса» (обмен ключа или токена на cookie) остаётся на форме входа только пока `TG_OWNER_ID` не задан: развёртывания без переменной сохраняют прежний вход, у настроенного — кнопки нет. Публичный ответ `/api/auth/config` отдаёт только булев флаг `owner_login`, не сам ID.

**Границы.** `STUDIO_API_KEY` и именные токены работают как раньше для API/MCP; `/api/session` (POST с ключом) остаётся для обратной совместимости и тестов. Если владелец раньше входил через Telegram как обычный пользователь, та учётка остаётся в реестре и на диске без изменений — миграции или слияния с корневой базой нет. В личном режиме (`STUDIO_PUBLIC=off`) Telegram-вход выключен, и `TG_OWNER_ID` ни на что не влияет.

API Telegram: [Login Widget](https://core.telegram.org/widgets/login), подпись проверяется в `accounts.verify_login` как раньше.
