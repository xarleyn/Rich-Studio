# 0014. Публичные учётки Telegram с отдельными базами

2026-10-30. Пользователь запросил публичный сервис: Telegram-вход, привязку своего канала и публикации из своей учётки. Это расширяет личный режим из ADR 0009.

**Решение.** `STUDIO_PUBLIC=on` включает официальный Telegram Login Widget. Сервер проверяет HMAC-SHA256 с ключом SHA256(bot token), возраст подписи (пять минут), одноразовый challenge и cookie того же браузера. Identity берётся только из подписанного Telegram id. Сессии и challenge хранятся хэшами в корневой базе; лимит попыток входа общий для всех процессов. Официальный widget загружается с telegram.org только на странице входа публичного режима; CSP разрешает этот скрипт и iframe oauth.telegram.org, без inline-скриптов и unsafe-eval.

**Изоляция.** Корневая база хранит учётки и прежние данные владельца. Каждая Telegram-учётка получает отдельную SQLite-базу и медиа под `accounts/<id>/`. `services.accounts.scope` через ContextVar связывает пути хранилища и политику транспорта; HTTP, MCP, фоновые задачи и worker threads наследуют этот контекст. Это сохраняет существующие запросы store, версии и идемпотентность без необязательного `WHERE owner_id` в каждом запросе. Миграции одинаковы для всех баз. Токены владельца и публичные сессии всегда читаются из корневой базы.

**Доступ к Telegram.** Привязка проверяет getChatMember для бота и пользователя. У учётки нет глобального канала или чата предпросмотра владельца. Все исходящие вызовы транспорта в контексте учётки проходят сервисную политику: канал должен быть привязан, используется сохранённый числовой id, права пользователя запрашиваются заново. Политика передаётся через контекст без импорта services из telegram. Входящие события Telegram могут отправить первый комментарий в проверенное обсуждение только после сопоставления с сохранённым постом. Отложка, восстановление sending, уборка и ежедневные копии проходят по всем учёткам под общей lease. Частичная публикация сохраняет успехи, даже если право в следующем канале уже отозвано.

**Цена и пределы.** Дополнительная база на учётку, проход по базам для очередей и маршрутизации событий. Это начальный публичный режим одного экземпляра с общим диском; он не обещает горизонтальное масштабирование. При росте нагрузки нужен общий индекс очередей и принадлежности событий или переход на общую БД с обязательной областью учётки. Нельзя масштабировать веб-часть на независимые диски. Litestream из текущего deploy реплицирует только корневую базу: внешний бэкап accounts/ и медиа обязателен для полного восстановления. Прежние данные не присваиваются Telegram-пользователю автоматически. Предложения из отдельного direct messages chat пока остаются в пространстве владельца; пользовательские API-токены и биллинг в этот срез не входят.

**Отказались.** От отдельного бота на каждого посетителя: пользователь запросил одного общего бота. От доверия Telegram id, присланному фронтендом без подписи. От привязки канала только по наличию в нём бота: любой пользователь мог бы публиковать в чужой канал. От OpenID-библиотеки и новой рантайм-зависимости: существующий механизм Telegram Login Widget проверяется стандартной библиотекой Python.
