# 0018. Импорт Telegram через отдельный транспорт чтения

2026-10-30. Сценарий — вставить ссылку чужого сообщения и получить редактируемый черновик с блоками,
HTML и Rich Markdown. Веб-виджет двух контрольных rich-постов возвращает заглушку; ссылка с темой
также требует отдельного разбора, иначе виджет выбирает ID темы как ID сообщения.

**Получение.** Используем Telethon 1.45.0 (MTProto layer 229): в установленном пакете проверены
`Message.rich_message`, `RichMessage.part`, `messages.GetRichMessageRequest`. Python SOCKS обеспечивает
отдельный HTTP CONNECT/SOCKS5-маршрут. Bot API остаётся транспортом публикации, его payload не меняется.
`copyMessage` не возвращает содержимое, `forwardMessage` создаёт сообщение; скрытые пересылки при чтении
URL не используются. Публичный виджет остаётся ограниченным fallback без подключения. Входящая пересылка
поддерживается только после явного одноразового запроса пользователя.

**Изоляция.** Сервис выбирает session-файл текущей учётки; транспорт сверяет авторизованный Telegram ID.
Общий режим использует только бота и публичные ссылки. Сессия владельца не служит общим доступом к чатам.
Коды входа вводятся локальным CLI, сессии не возвращаются API и не включаются в пользовательский экспорт.

**Преобразование.** Протокольный адаптер PageBlock/RichText → Bot API блоки отделён от редактора:
его формы по-прежнему строит спецификация. HTML и Rich Markdown создаются из этих блоков при импорте;
последующие ручные правки вкладок независимы. Неподдерживаемое содержимое получает видимую отметку и
предупреждение. Ссылка-источник сохраняется в `_studio`, в отправляемый payload не добавляется.

**Предел проверки.** Офлайн-тесты проверяют структуру, изоляцию, ограничения и запрет публикации.
Живая приёмка обоих исходных постов требует настроенных API ID/hash и доступа сессии; без неё
не утверждаем, что конкретные посты уже импортированы без потерь.
