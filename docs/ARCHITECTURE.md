# Как устроен код Rich Studio

Правило слоёв: **api / mcp_tools → services → telegram / store / spec**. Стрелки идут только вниз.

Рабочий сервер и CLI находятся в `src/`: один Rust-бинарник, Axum для HTTP и официальный rmcp для Streamable HTTP. `app/static/` остаётся редактором без сборки, `app/bundled/` содержит исходную спецификацию и публичные документы. Python-код в `app/` — проверяемый эталон миграции для разработки, он не входит в production-образ. Причины и граница совместимости: [0024](decisions/0024-rust-runtime.md).

Публичный режим (`STUDIO_PUBLIC=on`): `security::guard` проверяет credentials, создаёт `Principal` и кладёт отдельный `AppState` в extensions запроса. `ScopedState` в HTTP и `RequestContext` rmcp получают только этот контекст. `AccountContext` явно передаёт путь базы, папку медиа, Telegram ID и роль во все сервисы и хранилища. Фоновые задачи получают области из `services::accounts::all_contexts`; пользовательский запрос не выбирает путь другой учётки. Корневые auth-таблицы открываются через `Store::connect_root`. Транспорт перед вызовом Telegram проверяет привязку и актуальные права. См. [0014](decisions/0014-public-telegram-accounts.md).

События проверяют текущие права на канал, найденный по сохранённому объекту учётки; отказ не мешает другим учёткам. `send_linked_comment` разрешает конкретный ответ только после проверки исходного канала и текущего связанного обсуждения. Каждый `Store::connect` пользовательской базы применяет `max_page_count` из `ACCOUNT_DATABASE_MB`; корневая база не ограничивается. `StorageFull` и другие ошибки хранения после отправки сохраняют неопределённый результат ключа идемпотентности. HTTP отображает превышение квоты как 413, MCP как ошибку инструмента. См. [0016](decisions/0016-public-account-security-limits.md).

SQLite и синхронные файловые операции выполняются в конечных `spawn_blocking` задачах. Сетевые операции выполняются через Tokio; соединения SQLite не пересекают `await`. Отмена загрузки передаёт владение временным файлом завершающемуся файловому worker, который убирает его. Фоновые задачи принадлежат `Loops`: потеря lease отменяет их, остановка сначала прекращает новую работу и сохраняет lease до завершения HTTP-запросов, затем присоединяет задачи и освобождает lease.

## Сервер

`deploy/`: студия в образе из GHCR (uid 10001, read-only), Caddy с HTTPS, Litestream с копией базы в S3. Образ собирает `.github/workflows/image.yml`: каждый push в `main` — `:latest` (amd64), тег `v*` и ручной запуск — amd64 + arm64; Rust-зависимости зафиксированы в `Cargo.lock`, сборка использует `--locked`; в финальной стадии только бинарник, статика и сертификаты. Восстановление из реплики проверяет `scripts/restore_check.sh` (CI `restore.yml`, ежедневно). Решение: [0010](decisions/0010-server-image-and-pinned-spec.md).

## Политика ошибок при отправке

1. Строка поста пишется со статусом `sending` **до** вызова Telegram (и для немедленной отправки, и для отложенной). Если процесс умрёт между ответом Telegram и записью, строка останется, и следующий старт пометит её «мог уйти». Не получилось записать строку — в Telegram ничего не уходит. Отправка прошла → пост записан как `sent`. Всё, что после (закреп, комментарий, опрос `poll_after`), только добавляет предупреждения. Опрос после поста записывается отдельной строкой `kind=poll` (`sent` или `failed`); при сетевой ошибке его, как и пост, не повторяют.
2. Сетевая ошибка во время отправки, ответ 5xx или страница ошибки шлюза (`telegram.NoAnswer`) → «пост мог уйти, проверьте канал». Автоматического повтора нет. Повторять можно только то, что точно не ушло: `telegram.Unreachable` (соединение не установлено) и 429; планировщик возвращает такой пост в очередь (`retry_at`). Отложенный пост, опоздавший больше `SCHEDULE_LATE_MIN` (сервис был выключен), не отправляется, а получает статус `missed`.
3. Один канал упал → остальные всё равно отправляются; ответ 200, а `results[].ok` говорит, куда не ушло. Не ушло ни в один канал → ошибка, а не 200: так же для опроса, Live Photo и платного контента. Неудачная отправка (отказ Telegram или «мог уйти») записывается постом со статусом `failed` и текстом ошибки: её видно во вкладке «Посты» и в `list_posts`. Успешная отправка того же черновика в тот же канал убирает его прежние отказы; записи «мог уйти» остаются (в канале может быть дубль). `DELETE` убирает неудачную запись вручную. Отказ Telegram с кодом 400 отдаётся как 422 (запрос плохой, повтор не поможет), остальные ошибки Telegram как 502.
4. Предпросмотр уходит только в `TG_PREVIEW_CHAT` или в явно указанный chat_id, никогда в канал по умолчанию. Публикация без chat_id уходит в каналы черновика (`drafts.chat_ids`), а если их нет, в канал по умолчанию.
5. `Idempotency-Key` (`src/services/idempotency.rs`, таблица `idempotency`): повтор с тем же ключом возвращает первый результат; если первая попытка закончилась `MayHaveGone`, повтор получает ту же ошибку; если ничего не ушло, ключ освобождается. Только завершённые ключи истекают через сутки: `pending` и `uncertain` сохраняются, чтобы очистка не разрешила повтор неопределённой публикации.
6. Замена опубликованного поста (`posts.after_edit`) меняет в записи только текст и кнопки; ответы на кнопки и первый комментарий остаются, если новый пост не принёс свои. «message is not modified» от Telegram не ошибка.
7. Каждая замена поста через студию (`posts.edit`, `posts.edit_message`, `posts.set_buttons`) сначала кладёт прежнее содержимое в `post_versions`. Отложенный и пропущенный пост заменяется только пока он ждёт (`status in ('scheduled', 'missed')` в том же `UPDATE`): взятый планировщиком уходит с тем, что было. Редактор передаёт `post_version` прочитанного поста, при 409 показывает, что пост изменили, и заменяет только после подтверждения.
8. Кто отправил пост, пишется в `posts.actor` из `Principal::actor` и проверенного заголовка `X-Studio-Client` (`src/api/deps.rs`); редактор шлёт `ui`, без заголовка `api`.
9. Фоновые циклы (планировщик, getUpdates, восстановление `sending` после падения) ведёт ровно один процесс: тот, кто держит lease `loops` в таблице `meta` (`src/services/loops.rs`). При остановке планировщик не берёт новые посты, а начатые отправки получают `SHUTDOWN_GRACE` секунд; оборванная отмена отправка помечается «мог уйти». После аварийного перезапуска (lease не отдан) новый процесс берёт его, когда тот истечёт: до `LEASE_TTL` (60 с) планировщик и восстановление не работают. Продление lease, которое падает с ошибкой БД дольше `LEASE_TTL - RENEW`, переводит процесс в резерв, чтобы лидеров не стало два (срок считается по времени от последнего успешного продления). Ошибка не останавливает продление: когда БД оживёт, процесс снова возьмёт lease.
10. Замена содержимого поста (`edit`, кнопки) сначала берёт следующую `posts.version` (`store.claim_version`: один `UPDATE … RETURNING`, номер взятой версии приходит тем же запросом; нужен SQLite ≥ 3.35), потом идёт в Telegram: две правки одной версии не проходят обе, вторая получает 409. Отказ Telegram или студии возвращает версию (`store.release_version`); сетевая ошибка оставляет её занятой и отвечает «правка могла пройти». Замена и запись прежней версии в `post_versions` идут одной транзакцией.

При `TG_UPDATES_MODE=webhook` лидер фоновых циклов регистрирует webhook с секретом; HTTP-маршрут проверяет заголовок Telegram и атомарно занимает update_id в корневой базе до обработки. Повтор не запускает обработчик: при сбое во время обработки событие может потеряться, зато неопределённая отправка комментария не повторяется. Переключение обратно требует явного `deleteWebhook` у Telegram.

## Куда добавлять новое

Импорт Telegram: `src/services/imports/` создаёт новый черновик в текущем `AccountContext`;
`src/services/import_links.rs` разбирает URL, `src/services/import_web.rs` читает ограниченный публичный виджет, `src/services/import_forward.rs`
принимает явно запрошенную пересылку. `src/telegram/import_client.rs` — отдельный MTProto-транспорт чтения,
`src/spec/import_content/` — адаптер полученного содержимого и сериализация HTML/Markdown. Файлы
персональных сессий находятся в папке текущей учётки вне media/экспорта; общий режим входит только ботом.
Настройка — `src/import_login.rs`, решение и пределы — [0018](decisions/0018-telegram-message-import.md).


- Текстовые редакторы HTML/Markdown/JSON: компонент `static/js/components/rs-code-editor.js` принимает текст, спецификацию и каталог сниппетов; сообщает о правках через события. `source-completion.js` строит подсказки, `code.js` связывает события с состоянием поста и медиа. CodeMirror вендорен и загружается при открытии режима. Неприменённый JSON хранится в `S.pendingJson` и `_studio.buffers.json`; `buildPost()` его не отправляет. См. [0017](decisions/0017-source-editors.md).
- Новый метод Bot API для постов: функция в `src/services/posts.rs` + маршрут в `src/api/posts.rs` + тест в `tests/`.
- Новый тип сообщения (как опрос или Live Photo): запись в `src/services/kinds.rs` с проверкой, маршрут или инструмент MCP через `posts.send_kind`, диалог в редакторе. Отправка, планировщик, правка, кнопки и список постов берут остальное из записи.
- Новое событие от Telegram: ветка в `src/services/updates/` и тип в `ALLOWED_UPDATES`.
- Изменение схемы БД, новая колонка тоже: новый файл `app/store/migrations/NNNN_имя.sql` со следующим номером и записью в встроенном списке `src/store/db.rs` (старые не менять; `EXTRA_COLUMNS` закрыт). Номера идут подряд, повтор или пропуск останавливает запуск. Шаг выполняется в одной транзакции со своим номером, поэтому в файле не должно быть своих `begin`/`commit` и `vacuum`.
- Новая настройка: поле в `src/settings.rs::Settings` и чтение в `from_map` (числа через `number`, секреты через `secret`: ошибки попадают в общий список) + строка в `.env.example`; обязательные серверные настройки проверяются там же.
- Новый маршрут, который публикует или меняет канал: роль в `security::route_role`, идемпотентность и `Principal::actor`; тесты в `tests/rust/`. Для MCP согласуйте `tool_role`, annotations/schema в `src/mcp_tools/contract.json` и обработчик области. `make docs` пересобирает справочники из бинарника.
- Новый фоновый цикл: задача в `services::loops::Worker` или `services::maintenance` (запускается под lease, только в одном процессе) и строки по [OBSERVABILITY.md](OBSERVABILITY.md#куда-добавлять-новое).
- Новая проверка состояния, событие в журнале или фоновый цикл: [OBSERVABILITY.md](OBSERVABILITY.md#куда-добавлять-новое).

## Тесты

- `cargo nextest run --workspace --locked --no-fail-fast` — Rust-контракты HTTP/MCP, SQLite, права, сбои отправки, фоновые задачи и CLI. `make e2e-rust` запускает прежние браузерные сценарии на изолированной Rust-сборке и mock Telegram.
- `tests/mock_telegram.py` — только dev-стенд для браузерных сценариев (`make mock`, `make dev`, `make e2e`); Rust-тесты от него не зависят. Опциональная внешняя проверка: `docs/TGFAKE.md`.
- `npm run test:lock` — `scripts/check-python-lock.mjs`: `requirements.txt` и `requirements.lock` согласованы.
- `npm run test:docs` — `scripts/generate-rust-docs.mjs --check`: `docs/openapi.json` и `docs/reference/` совпадают с Rust-бинарником; `make check-docs` собирает его и запускает проверку.
- `tests/e2e_ui.mjs` — раннер браузерных проверок против запущенной студии и `tests/mock_telegram.py`; сами проверки — по файлу на каждую в `tests/e2e/`.
- `npm run test:render` — `tests/render_unit.mjs`: очистка HTML/Markdown в render.js на враждебных примерах (script, on*, javascript:, svg, mXSS), без студии. Новая дыра в санитайзере → сначала пример сюда.
- `npm run test:parity` — `tests/render_parity.mjs`: предпросмотр каждого примера из `tests/telegram_parse/captured.json` совпадает с предпросмотром блоков, которые для него вернул настоящий Telegram. Новый пример: добавить в `cases.json` и записать `scripts/capture_telegram_parse.py` (нужен токен и чат, сообщения сразу удаляются). Осознанное расхождение помечается `known_gap` с причиной.
- `npm run lint` — ESLint для `app/static` и тестов на JS: ловит неопределённые имена и забытые импорты, которые браузер покажет только при клике.
- Перед PR: `make docs`, `make check`, `make e2e-rust`. `check-rust` включает fmt, Clippy без предупреждений, nextest, doctests, cargo-deny, cargo-machete и release-сборку; `check-docs` сверяет документацию. Контейнерную проверку запускает `scripts/check-rust-container.mjs`; она подтверждает установленный бинарник, отсутствие Python, сохранение данных и остановку, отдельно от локальных тестов.
