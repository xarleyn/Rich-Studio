# Rust runtime

Ветка `rust-rewrite` собирает один бинарник `rich-studio`. Он читает существующие переменные окружения через `Settings::from_env`, открывает прежнюю SQLite-базу и применяет неизменённые SQL-миграции. Миграции, bundled-спецификация и ресурсы MCP-preview встроены при сборке.

`rusqlite` 0.41.1 включает SQLite 3.54.1. Не возвращайте SQLite 3.51.0/3.51.1:
при параллельном открытии и закрытии WAL-соединений в Unix эти версии могут зависнуть.
Минимальную исправленную версию и завершение конкурентных операций проверяют отдельные
runtime-тесты; [подробности обнаружения и повторной приёмки](RUST_SQLITE_WAL_FIX.md).

Редактор остаётся отдельным каталогом статических файлов. Путь выбирается так: `STUDIO_STATIC_DIR`, затем `static` рядом с исполняемым файлом, затем `app/static` относительно рабочего каталога. Это позволяет запускать приложение без исходного checkout. Сервер останавливается по Ctrl-C или SIGTERM: прекращает брать новые фоновые задания, сохраняет lease до завершения принятых запросов, затем завершает фоновые задачи и сбрасывает журнал. `SHUTDOWN_GRACE` ограничивает ожидание; прерванная отправка остаётся записанной для восстановления без автоматического повтора.

За reverse proxy `FORWARDED_ALLOW_IPS` задаёт доверенные IP/CIDR через запятую (по умолчанию `127.0.0.1`); пустое значение отключает доверие. `X-Forwarded-For` влияет на лимит входа только от доверенного TCP-узла, цепочка разбирается справа налево. `*` в `deploy/docker-compose.yml` предназначена для закрытого порта, до которого доходит только Caddy. Недоверенный или некорректный заголовок не позволяет посетителю сменить свой счётчик входа.

Публичный сайт содержит 12 канонических страниц RU/EN, в том числе `/features/` и его перевод. Даты sitemap и Schema.org берутся из `app/bundled/public-site-seo.json`, встроенного при сборке. Обновляйте каталог вместе с HTML и пересобирайте бинарник. Ресурсы с подтверждённым хэшем в `?v=` получают годовой кэш, остальные требуют ревалидации; Brotli-копии CSS/JS готовятся заранее. Проверка публичного HTTP-контракта после выкладки: `node scripts/check-public-seo.mjs --site https://example.com --app https://app.example.com --www https://www.example.com`. Порядок обновления www и проверки индексации: [SEARCH.md](SEARCH.md).

Команды оператора:

```sh
rich-studio serve
rich-studio token add operator --level admin
rich-studio token list
rich-studio token revoke operator
rich-studio import-login
rich-studio import-login --account 123456789
rich-studio healthcheck
rich-studio request GET /api/drafts
rich-studio openapi
rich-studio mcp-contract
```

`token add` печатает секрет один раз; в базе остаётся прежний SHA-256. Отзыв закрывает связанные сессии. `request` обращается к локальному серверу на `STUDIO_BIND`, берёт bearer из `STUDIO_TOKEN` и не принимает секрет аргументом командной строки. `healthcheck` проверяет `/readyz`; для другого адреса есть `--url`. `/readyz` раскрывает только имена неуспешных проверок. `/api/health` требует обычный доступ к API и сохраняет формат отчёта с `checks`, `problems`, `status` и временем проверки.

`import-login` использует `TG_IMPORT_API_ID` и `TG_IMPORT_API_HASH`; телефон, код и пароль двухэтапного входа вводятся в терминале скрыто. С `--account` перед сохранением проверяется Telegram ID. Без него настраивается владелец корневого пространства. Уже существующий файл сессии команда не перезаписывает. Сессия сохраняется в прежнем формате Telethon StringSession, права файла на Unix — `0600`.

Журнал JSON пишет отдельный ограниченный обработчик: `X-Request-ID` связывает события одного запроса, секреты и содержимое постов скрываются. Глобальный журнал и метрики доступны только оператору; отчёт публичного пользователя описывает его собственную очередь. Проверки фоновых циклов используют действительный lease и зарегистрированные отметки выполнения. Удаление неиспользуемых файлов и старых версий включается только `MEDIA_UNUSED_DAYS` и `VERSIONS_KEEP`; неопределённые отправки и их ключи уборка сохраняет.

ZIP-экспорт использует SQLite Online Backup и прежние пути `studio.db`, `media/`, `accounts/<id>/…`. Он сохраняет полную базу с хэшами доступа для восстановления и доступен оператору с правом admin. Файлы сессий импорта и `.env` в архив не попадают. Ежедневные снимки и срок хранения управляются `BACKUP_KEEP`.

Docker использует отдельные стадии сборки и исполнения: зафиксированный Rust toolchain, `cargo build --release --locked`, Debian с сертификатами, бинарник и статика. В конечном образе нет Python, pip и исходного Python-сервера. Сохранены uid 10001, `/data`, порт 8080, работа с read-only root и проверка восстановления через Litestream. Команды восстановления вызывает сам бинарник.

Проверки переноса:

```sh
cargo test --locked --test runtime
make check
make docs
make e2e-rust
docker build -t rich-studio-rust-candidate .
IMAGE=rich-studio-rust-candidate node scripts/check-rust-container.mjs
IMAGE=rich-studio-rust-candidate scripts/restore_check.sh
```

`tests/rust/runtime.rs` запускает скопированный бинарник из временного каталога, проверяет выбранный `DATA_DIR`, сохранение черновика, встроенную спецификацию, точное совпадение SQL с исходными миграциями, CLI-healthcheck и совместимость токенов. `make e2e-rust` использует чистое окружение и временные данные; на Windows копирует бинарник, чтобы проверка не мешала новой сборке. Контейнерная проверка отключает внешнюю сеть, проверяет отсутствие Python, uid 10001, read-only root, сохранение токена и черновика после перезапуска, код выхода при SIGTERM. Проверка Litestream создаёт отдельные том, проект и реплику, затем восстанавливает токен и черновик.

CI запускает Rust quality gates и браузерные сценарии против Rust; Python-тесты продолжают проверять эталон. Для локальной разработки нужны Cargo, Node, GNU make с POSIX shell и Python с тестовыми зависимостями. На Windows `Makefile` находит `.venv/Scripts/python.exe`; команды контейнера и генераторы также запускаются напрямую из PowerShell (`$env:IMAGE='rich-studio-rust-candidate'`). Shell-проверка восстановления работает в Git Bash и Linux.

Это описание механизма запуска кандидата, а не разрешение обновить действующую установку. Полная готовность требует всех срезов [плана переноса](superpowers/plans/2026-10-31-rust-backend-rewrite.md), полного `make check`, браузерных проверок и контейнерной проверки. Наличие бинарника или успешный `/healthz` не подтверждает весь функционал, MTProto-импорт и безопасность перехода очереди. Фактически выполненные проверки и границы подтверждения записаны в [отчёте приёмки](RUST_MIGRATION_ACCEPTANCE.md).
